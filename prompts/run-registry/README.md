# Campaign — the run registry

## 0. Why this campaign exists

This project has entered a phase where single measurements take hours. On 2026-09-20 and 21, in one
working session, the following happened:

1. **A three-hour measurement was lost because its results lived in memory.**
   `realistic_large_x.py` accumulated every cell into a list and printed its tables only after the
   last one. When the run was killed at 4 h 57 m, `full.out` contained one line — the
   `<!-- generated by -->` marker. Only per-cell wall times survived, on stderr.
2. **A run was orphaned from the agent that started it**, became `PPID 1`, and left nothing on disk
   saying what it was, who owned it, what it was for, or how far along it was. Reconstructing that
   took `ps`, `lsof` and a stderr file, and only happened because someone went looking.
3. **Nineteen poll loops accumulated and none of them could ever exit.** Each polled with
   `pgrep -f <script-name>`, which matches the waiting shell's *own* command line, so the condition
   was never satisfiable. Fifteen were waiting on a measurement that had already been killed; two
   had been spinning for five hours on a script that finished in the first minute; one was waiting
   for a file to reach seventeen lines that its dead producer had left at sixteen. Every one was a
   full conversational turn that re-sent an entire context and learned nothing.
4. **A datastore was written into a session scratchpad and is gone.** The 462-row type/quality
   census in `docs/source-remediation-verification.md` §4.2 cannot be re-examined, and
   `prompts/handover` prompt 03's requirement to reproduce its shape "on the same datastore" is
   therefore unsatisfiable. Session scratchpads are per-session; 131 others survive, that one does
   not.
5. **Resumption was assumed rather than exercised.** When a 10 h 33 m pipeline run was finally
   resumed, it replayed every earlier stage correctly and then crashed on a read-back path that had
   never been taken — `prompts/datastore-readback` §0. Nobody had resumed anything past that stage
   before.

None of these is exotic. All five are the ordinary consequences of treating a long-running job as
something a conversation owns.

**0.1 What already works, and should be generalised rather than reinvented.** The rewritten
`realistic_large_x.py` appends each cell to a JSON-Lines file and `fsync`s it, stamps each record
with a SHA-256 of its own source and the `git rev-parse HEAD`, and rebuilds every table from those
records alone. On its first outing the provenance stamp paid for itself: re-running the script
after the commit reported the same script hash and reused all sixty cells, which *proved in four
seconds* that the committed script was byte-identical to the one that produced the published
numbers. That is the pattern. It is currently one script's private arrangement.

**0.2 The registry is about existence, not computation.** Two different things got conflated in the
discussion that produced this campaign, and the prompts keep them apart:

- **The registry** records that a job exists, what it is for, who started it, what tree it ran
  against, whether it is alive, and how far it has got. This is what makes a run survive a session
  ending, a quota interruption, or a switch between accounts.
- **Checkpointing** is per-job and is sometimes already solved. A measurement script with a natural
  unit of work needs one. A `main.py` pipeline run already has one — its datastore — and needs
  only to be *registered*, not re-plumbed.

**0.3 Correctness is the only objective.** Sequence by epistemic dependency. A registry that nobody
reads is worse than none, because it looks like coverage; so the discovery rule matters as much as
the file format.

## 1. Scope

**In scope:** a small shared helper, the `var/runs/` layout, a lister, the launch and liveness
rules, and the `CLAUDE.md` section that makes them binding. Then adoption by the existing
long-running entry points.

**Out of scope:** any physics; any production compute path; `ComputeTargets/`, `CosmologyModels/`,
`LiouvilleGreen/`, `AdaptiveLevin/`, `Datastore/`, `main.py`, `config/`, `docs/spec/`. This campaign
changes how jobs are *launched and tracked*, never what they compute.

**Explicitly not in scope:** a scheduler, a queue, a daemon, a web UI, or anything that runs when
nobody asked it to. The whole thing should be a few dozen lines plus a convention.

- `var/runs/realistic_large_x_cells.jsonl` — 60 cells, single script hash `c1cd3598c23a`. It backs
  the published tables in `docs/handover/REALISTIC-LARGE-X.md`, and `realistic_large_x.py` gates

## 5. The rules this campaign runs under

The project-wide ones in `CLAUDE.md`, plus the campaign invariants:

1. **One commit per prompt.**
2. **Every prompt writes a log** to `logs/NN-<name>.md`, classifying every deviation as
   `STRUCTURALLY REQUIRED`, `IMPLEMENTATION CHOICE` or `UNINTENDED DRIFT`.
3. **Every prompt updates `IMPLEMENTATION_STATE.md` in its own commit**, plus `docs/OPEN_ISSUES.md`.
4. **Do not fix things the prompt did not ask for.** Record them and open a §3 issue.
5. **Commit messages** in `CLAUDE.md`'s form, ending with `Co-Authored-By:` naming the model.
6. **Verification documents are additive.**
7. **No speculative generality.** Every field in the manifest must be justified by something in §0
   that would have been caught by it. A field nobody will read is a field that will go stale.

### 5.1 The log template

Subject, commit, result; **What shipped**; **Deviations from the prompt** (each classified);
**Verification performed**; **Observations not acted on**; **State handed to the next prompt**.
