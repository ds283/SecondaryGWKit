# Run registry campaign — implementation state

**Last updated:** 2026-09-22 · **Status: COMPLETE — 3 of 3 prompts landed (01, 02, 03).** Prompt 01
landed the `RunRegistry/` package, the `var/runs/` layout, the lister, and the six rules as a
`CLAUDE.md` section. **The self-match regression is in the tree and bites**: the same test fails
against a `pgrep`-based implementation and passes against the shipped one. Prompt 02 adopted it in
`docs/gktk-remedial/scoped_pipeline_run.py` behind an opt-in `--register`, and **left the
`realistic_large_x.py` hash hazard alone on purpose** — that script still has 60 cells at script
hash `c1cd3598c23a`, and no existing checkpoint record was re-stamped, migrated or regenerated by
anything in this campaign. Prompt 03 split the manifest's overloaded `checkpoint` field in two —
`checkpoint` is the unit ledger, `results` names the durable store a job's results live in — so
`record()` cannot append JSON-Lines to a datastore and `known()` cannot report "nothing done" for a
file that is not a ledger. Two issues are open in §3; one is resolved in §4.

## 3. Active and unresolved issues

- **[01-var-runs-holds-unattributable-loose-files]** *(opened 2026-09-22 by prompt 01)* — four
  files sit at the top level of `var/runs/`, beside the two A3 pilot directories, with nothing
  saying which run they belong to: `run.out` (23,616 bytes, 2026-09-20T17:08), `run.pid` (6 bytes,
  2026-09-20T14:09), `run.progress` (3,504 bytes) and `realistic_large_x_cells.jsonl` (60,484
  bytes, 60 cells). Three of the four are exactly the artefacts the registry now gives a home to —
  a stdout capture, a pid and a progress file — and the mtimes suggest, but do not establish, that
  they belong to the `realistic_large_x.py` run of 2026-09-20 rather than to either A3 attempt.
  This is README §0 item 2 in its residual form: the files survived, the attribution did not.
  **Impact:** low and bounded. The lister ignores them correctly (it lists directories), nothing
  reads `run.pid` or `run.progress`, and `realistic_large_x_cells.jsonl` is load-bearing and
  correctly placed — its path is in `realistic_large_x.py`'s own docstring, which is its
  attribution. What is lost is the other three's. **Next step:** prompt 02, which is the prompt
  entitled to touch `realistic_large_x.py` and to decide where a registered run's outputs go, may
  record in its log which run each file came from if it can establish it from the file contents —
  **but must not move, rename or delete any of them**, per campaign README §4 and prompt 01 §3.
  Deliberately not acted on here: prompt 01 may only *read* `var/`. Measurement:
  [`logs/01-the-run-registry.md`](logs/01-the-run-registry.md), "Observations not acted on" item 1.
  Indexed at `docs/OPEN_ISSUES.md` §1.11.
  **Narrowed 2026-09-22 by prompt 02, which established the attribution from the file contents and
  moved nothing.** All four files are the *successful* `realistic_large_x.py` run of 2026-09-20 —
  the one that produced the sixty cells, not the 4 h 57 m attempt README §0 item 1 describes.
  `run.progress` is that script's **stderr**: its first line is the script's own checkpoint notice,
  naming `var/runs/realistic_large_x_cells.jsonl`, script hash `c1cd3598c23a` and HEAD
  `c414451b90d9`, and it ends at `[ 10770 s] together x_resp=1e+08 realistic/open`. `run.out` is
  the same run's **stdout** — it opens with `<!-- generated by docs/handover/realistic_large_x.py
  -->` and closes with "Cells: 60 computed or read from the checkpoint … This invocation: 10772 s".
  `run.pid` holds `21928` at mtime **14:09**, and 17:08 − 10,772 s = **14:08:28**, so the pid file
  is that run's, written at launch. **What is left open** is only that none of this is legible
  *on disk*: the attribution now lives in a log and on this board, and the remedies — renaming the
  three files or dropping a note beside them — are both forbidden to this campaign (README §4).
  A later prompt with a grant over `var/runs/` may act; nothing depends on it.

- **[02-realistic-large-x-is-outside-the-registry]** *(opened 2026-09-22 by prompt 02)* —
  `docs/handover/realistic_large_x.py` is **deliberately not** a registry client, per prompt 02 §2,
  and this row exists so that whoever proposes to change that knows the price first.
  **The hazard, stated plainly:** the script gates checkpoint reuse on a SHA-256 of its own source
  (`script_sha256()` at :160, `load_checkpoint()` at :394), so **editing it by one character — a
  comment, a blank line, an import — discards all sixty records** in
  `var/runs/realistic_large_x_cells.jsonl` and costs a **three-hour** recomputation (the run that
  produced them took 10,772 s). Those cells are every number in every table of
  `docs/handover/REALISTIC-LARGE-X.md`. **Impact of leaving it:** nil today. It has never been
  orphaned; it is a single-process job with no Ray, its checkpoint path is in its own docstring,
  and its provenance stamp is the pattern `RunRegistry` was copied from rather than something it
  lacks. What it does not get is a manifest and a heartbeat, so a *future* run of it is
  discoverable only by whoever launched it — the same gap as before, for a script that is
  finished. **Next step, for a campaign that wants it registered:** do it in the same commit as
  some other edit that is already going to cost the recomputation, and budget the three hours;
  **never** re-stamp the existing records to preserve reuse, which would make the provenance stamp
  assert something false and is prompt 02 §6's third stop condition. Reasoning:
  [`logs/02-adopt-the-registry.md`](logs/02-adopt-the-registry.md) §3. Also noted on the
  `handover` board's **A2** row, which owns `REALISTIC-LARGE-X.md`. Indexed at
  `docs/OPEN_ISSUES.md` §1.11.

## 4. Resolved issues

- **[02-a-datastore-checkpoint-path-would-be-appended-to-by-record]** *(opened 2026-09-22 by
  prompt 02)* — a registered pipeline run puts its **datastore** path in the manifest's
  `checkpoint` field, because README §0.2 says that is what its checkpoint is and a resume needs
  to know it. But `Run.record()` treats `checkpoint` as an append-only JSON-Lines file, so calling
  `record()` on such a run would append a JSON object to a **SQLite file**. **Impact:** latent and
  narrow. Nothing calls it — `scoped_pipeline_run.py` never calls `record()` or `known()`, and the
  driver says so in a comment at the `begin()` call — and `known()` on a binary file returns
  nothing rather than raising, since every line fails to parse. The exposure is a *future* script
  that copies the pipeline pattern and then adds units. **Next step:** either `record()` refuses a
  `checkpoint` that is not a `.jsonl` path, or the manifest grows a separate field for "the
  durable thing this job's results live in" and `checkpoint` keeps its narrower meaning. The first
  is one line; the second is the honest one, and neither was in prompt 02's grant. Measurement:
  [`logs/02-adopt-the-registry.md`](logs/02-adopt-the-registry.md), "Observations not acted on"
  item 2. Indexed at `docs/OPEN_ISSUES.md` §1.11.
  **Assigned (2026-09-22):** prompt 03,
  [`03-the-checkpoint-field-means-two-things.md`](03-the-checkpoint-field-means-two-things.md), which
  takes the second of the two repairs named above — the honest one.
  **Resolved 2026-09-22 by prompt 03**, commit *"Split the manifest's overloaded checkpoint field
  in two"*. The manifest now carries the two meanings as two fields: `checkpoint` is the unit
  ledger and nothing else, and `results` names the durable store a job's results live in.
  `record()` reads only `checkpoint` and **refuses by name** when there is none, quoting the
  results store it will not write to — demonstrated by writing not-JSON into that store and
  comparing the bytes after the refusal, not merely by catching the exception. `known()` no longer
  answers `{}` for a file that is not a ledger, while still answering `{}` quietly for a ledger
  that does not exist yet and still tolerating a torn final line.
  `docs/gktk-remedial/scoped_pipeline_run.py` names its datastore in `results`, and the text
  `main.py` is handed is byte-identical to before. **The repair cost nothing** because the window
  was open: `find var/runs -name manifest.json` printed nothing, so no manifest had to be migrated,
  re-meaned or shimmed. Measurement:
  [`logs/03-the-checkpoint-field-means-two-things.md`](logs/03-the-checkpoint-field-means-two-things.md).
  Row deleted from `docs/OPEN_ISSUES.md` in the same commit.

The other two issues this campaign opened are still in §3, and that is the honest count rather than
a failing: both are a **deliberate non-adoption** recorded so its price is known, not work left half
done.
