## Deviations from the prompt

### 1. The exact flavour's gap is a region truncation, not `drop_first_WKB_sample` — STRUCTURALLY REQUIRED

**The prompt assumed** (§2's axis table) that the seam axis could be driven by one mechanism in
both flavours: "gap closed (`Fixture` as built) · gap open (`drop_first_WKB_sample=True`)".

**What was actually there.** `drop_first_WKB_sample` is **inert in the exact flavour**.
`Case.Tk_builder` returns an `ExactTkFunctions`, which ignores the sampled `(Tk_numeric, Tk_WKB)`
inputs entirely and declares `WKB_region = (crossover_z, 0.0)` from a closed form valid at every
$z$. Dropping a sample from a fixture the builder never reads changes nothing, so the factorial's
second cell would have been bit-identical to its first and the flavour × seam interaction would
have been unmeasurable.

**What was done instead.** `_GappedExactTkFunctions` declares `WKB_region[0]` to sit one gap below
`crossover_z`, where the gap is *the same number* the dropped fixture opens — the fixture's own
first WKB grid step in $\log(1+z)$. `build_partition` computes the same shortfall and `_ClampedTk`
applies the same hold, to closed-form accessors instead of splined ones.

**This is measured, not assumed, twice over.** Table 6 runs the prompt's literal mechanism in the
exact flavour on all three shapes and records the totals as identical **bit for bit** (relative
difference exactly `0.0e+00`) with no gap recorded. Table 2 then shows the recorded `gap Tq` and
`gap Tr` agreeing across the two flavours to all four printed digits at every rung. And §4's
result is the validation that matters: the clamp term measured on exact ingredients and on
realistic ones agrees to **five significant figures** at all fourteen rungs where both exist
(worst-conditioned rung: $+4.593496\times10^{-1}$ against $+4.593416\times10^{-1}$). Two mechanisms
opening materially different gaps could not produce that agreement, so **the gap-open cells are
comparable across flavours and the attribution is not weakened by the substitution.**

### 2. `q-smooth` realistic stops at $x_{\rm resp} = 10^5$ — STRUCTURALLY REQUIRED

**The prompt assumed** (§2) the realistic flavour would run the full ladder, "$980$ to $10^7$–$10^8$
as each shape's fixtures reach", and §3 item 1 anticipated that the binding cost might be fixture
**set-up**.

**What was actually there.** Set-up is flat and cheap in both flavours (deviation-free; see
"Verification performed"). The realistic **integral** is what grows, and it grows at a rate that
differs by shape: mean factor per decade of $x_{\rm resp}$ is 1.7× (`together`), 3.6× (`T-first`)
and **8.6×** (`q-smooth`). At 8.6× per decade `q-smooth`'s $10^6$ pair is hours each and its $10^7$
pair of order twelve hours each.

**What was done instead.** `REALISTIC_CEILING` is a per-shape dict, `{"together": 1e8, "T-first":
1e7, "q-smooth": 1e5}`. The four `q-smooth` realistic cells above $10^5$ are printed as **not
reached** in Tables 2, 7 and 8, with the measured cost curve beside them, and the ceiling is
reported in §7 and §8 item 5 as prompt §7's second stop condition met by measurement. The exact
cells are cheap at every rung and are run at all of them, so the control table and the exact clamp
column are complete to $10^8$/$10^7$. **Nothing fell back to the exact flavour and no cell was
dropped silently.**

A corroborating lower bound, labelled as such wherever it appears: an earlier run of this harness
was killed while computing `q-smooth` realistic at $x_{\rm resp} = 10^6$, closed seam, after more
than **5600 s without completing**. No $N$ value from that run appears anywhere in the document or
this log; only that timing.

**Origin.** The cap was escalated to the user, who set it. The measurement is mine; the choice of
rung is theirs.

### 3. The script checkpoints each cell to disk, with provenance — IMPLEMENTATION CHOICE

**The prompt left it open.** It asked for one command and a recorded runtime, and said nothing
about how a three-hour run should survive an interruption.

**Alternatives considered.** (a) Buffer everything and print at the end — what the first version
did, and it is how `large_x.py` works, which is reasonable for an eleven-second script. (b) Print
tables incrementally — rejected, because every table is cross-block and cannot be emitted until
the last cell lands. (c) A JSON-Lines side-file appended and `fsync`ed per cell, read back on the
next run. **(c) was chosen**, after two multi-hour runs were lost whole: a rate limit took the
first, and my own bulk `kill` of some stuck poller shells took the second at 4 h 57 m. With (a) the
cost of any interruption is the entire run; with (c) it is one cell. `run_cell` therefore returns
only JSON-able scalars — including its own 50-digit reference — and **no table reads a live
`Case`**, so the whole document is reproducible from the file.

Three sub-choices a later reader may wish to disagree with:

- **Location.** `var/runs/realistic_large_x_cells.jsonl` under the repository root, gitignored,
  overridable with `REALISTIC_LARGE_X_CHECKPOINT`. The first version defaulted to
  `tempfile.gettempdir()`; that was wrong, because macOS reaps that directory periodically and
  nobody who has not read the script would look there. A file whose purpose is to survive an
  interruption should not live somewhere the OS may delete it.
- **Provenance.** Every record carries the SHA-256 of the script's own source, `git rev-parse
  HEAD`, and a flag for an unclean tree, as they stood when the cell ran. Without it a cell
  computed by one version of `run_cell` would be silently reused by a changed one — the wrong
  failure to leave open in a repository whose campaign discipline is entirely about provenance.
- **On a hash mismatch: discard and recompute, with a notice on stderr naming both hashes and the
  count.** The alternative is to refuse and exit. Discarding was chosen so that an edited script is
  self-healing rather than stranding an operator on a file they must know to delete; the notice is
  what keeps the discard visible. Records are never blended across script versions. Cells that
  *raise* are recorded too, with their reason, so a permanent failure is durable; a cell killed
  mid-flight writes nothing and is simply recomputed, which is the distinction between a failure
  the code produced and an interruption imposed on it.
