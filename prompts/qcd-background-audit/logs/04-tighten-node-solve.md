**Why `xtol=1e-300, rtol=1e-14` and not some other pair (prompt §2 item 1):** `rtol=1e-14` sits
just above Brent's own convergence floor of `4*eps ≈ 8.9e-16` — tighter would ask `root_scalar` for
precision it cannot deliver from a bracketing method, and this is exactly the tolerance
`CosmologyModels/tests/T_z_reference.py`'s `accurate_T` (the campaign's independent reference) was
already built to use, so the shipped solve and the reference now use literally the same
tolerance and the same algorithm on the same equation. `xtol=1e-300` (SciPy 1.15.2 on this tree
accepts it without complaint — no rejection, no clamping observed) removes the absolute component
from the stopping rule entirely: `T` spans about twenty decades over the tabulated range
(`z ∈ [-0.2, 1e20]`), so any finite absolute tolerance binds at the cold end long before the hot
end is resolved, which is exactly what the shipped `xtol=1e-6` did. With `xtol` disabled,
`rtol` alone decides convergence at every temperature.

## Deviations from the prompt

### 1. `T_PHOTON_MAX` loosens from `7.2e-04` to `7.27e-04` — IMPLEMENTATION CHOICE, anticipated by the prompt itself

The prompt's own acceptance table (§3) and README §6.1's "After 04" column both state the max is
expected to move from 7.177e-04 to ~7.26e-04 — worse, not better — because the max is pinned at
the un-segmented jump height (T4, prompt 06's), not set by node accuracy, and a different set of
now-accurate nodes happens to bracket the jump slightly differently. Measured: 7.2615e-04. I
tightened `T_PHOTON_P90` and `T_PHOTON_MEDIAN` (which the fix does improve) and set `T_PHOTON_MAX`
to `7.27e-04`, just above the achieved value, following the same "round up in the last place
quoted" convention prompt 01 used. I read this as governed by the prompt's explicit instruction to
"tighten prompt 01's test thresholds 1 and 2 to the achieved values (README §6.1's 'After 04'
column)" rather than by §2 item 5's "a tolerance may only tighten or stay" rule, which is about the
downstream `ComputeTargets/tests/` suite prompt 02's map covers — because README's own acceptance
table names this exact number as the correct, planned outcome of landing 04 before 05/06, not an
unexpected finding. I did not treat this as one of the "more than one tolerance loosens, stop and
ask" instances for that reason.

### 2. Two `ComputeTargets/tests/` assertions needed the branch-crossing location updated, not just re-scored — STRUCTURALLY REQUIRED

`_temperature_crossing_log1pz` root-solves `T_photon(z) - T_break` **on the shipped spline**
(`LambdaCDM_GenericEOS.py:275-307`) to locate each `integration_break_points` crossing. Because the
shipped representation is a single continuous spline that runs straight across the genuine jump
(the defect T4/prompt 06 exists to fix), this is a legitimate root-find on a continuous function —
not the no-root trap README §2 (b) warns about, which applies only to the true step function. But
it means the crossing's *location* depends on the spline's node values, and tightening those moved
it: worst case (`T_120_MEV`, 0.12 GeV) by 1.334557e-05 relative in `u = log(1+z)`.

Two tests hardcode that location:

- `test_background_tau.py::test_qcd_break_points` checks every computed break point lands within
  `1e-9` of the corresponding `branch_boundaries` entry in the JSON's `convergence` block. That
  block is written by `docs/gktk-remedial/residual_convergence.py`, which prompt 02's generator
  does not touch (`[01-convergence-block-has-a-separate-generator]`) and which prompt 04 is not
  scoped to regenerate. The prompt's own map anticipated exactly this: "prompts 04-07 must not
  assume this script regenerates the convergence block... should say so in their own logs if a
  convergence-scored test's accuracy figure... moves." I loosened the alignment tolerance from
  `1e-9` to `1.4e-05` (measured worst case), named as a module constant with a comment attributing
  it to the stale `convergence` block rather than to any new inaccuracy, and pointed at the issue
  that closes it (prompt 08, when `residual_convergence.py` is re-run).
- `test_numeric_break_points.py::test_the_branch_crossing_is_inside_the_range` asserts the crossing
  equals a hardcoded closed-form-style literal, `8.64355463e11`, to `places=6`. I updated the
  literal to `8.64366999e11` (the newly measured location) and left `places=6` — the same
  precision — unchanged, since this is a golden value that moved with the representation, the same
  class of update as regenerating the JSON, not a loosening of what is asserted.

Both are explicitly authorised by the prompt's "files you may touch" list (both modules are named
in prompt 02's map) under "tolerances, thresholds and comments only." I judge the resulting total
of **one** loosened tolerance (`QCD_BREAK_POINT_ALIGNMENT_TOL`) against §2 item 5's "if more than
one has to loosen, stop and ask" — the branch-crossing literal update is a re-scored golden value,
not a loosened tolerance, so it does not count toward that total.

### 3. The $\omega^2/\omega_0^2$ scatter did not narrow — IMPLEMENTATION CHOICE (measured, not changed, per the prompt)

Prompt §2 item 3(b) asks for a measurement, not a fix, and says a narrowing (if found) would be
